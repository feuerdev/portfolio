Host administration is outside scope. Source assessments describe the original reviewed commits; subsequent cleanup is recorded in [delivery.md](delivery.md).

[The inventory snapshot](inventory.json) records the reviewed default commits, file counts and metadata. Inspected default-branch file trees, READMEs, manifests/dependency files, local instructions, and representative implementation paths. Also inspected feuer's `dev` branch because its README identifies it as the more advanced version. Fork assessments credit visible personal changes, not the whole upstream project. No user analytics, sales, active-user counts or business validation were available. GitHub stars indicate interest, not users or willingness to pay. Latest push timestamps can describe branch activity; they do not prove an app still works.

Each dimension is 1–5, with higher better: **P** portfolio value of further work (35%), **G** plausible paid offering (20%), **F** finishability of a useful narrow release (20%), **E** evidence from existing implementation, tests and interest (15%), **M** manageable maintenance/platform burden (10%). Total = `7P + 4G + 4F + 3E + 2M`, maximum 100. Five means exceptional; one means little demonstrated value/high friction. The paid scores are hypotheses, not validated demand. Ties favor the clearer next deliverable. Effort estimates are focused engineering days after prerequisites; discovery, waiting for store review and external access are additional.

## Repository assessments and evidence

**keep-mcp — first priority.** Python MCP tools for Google Keep notes, checklists, labels, collaborators and media. Source includes serialized access to the Keep client, mutation guards and regression tests; CI checks Python 3.10–3.12 and coverage; a release workflow publishes to PyPI. The 5 October snapshot shows **103 stars**, versus at most two on every other repository here. This is the clearest evidence of external interest. The README's label guard is broader than “created by this server”: existing notes with the label can also be modified, and some operations have different scope. Authentication relies on unofficial gkeepapi and a powerful account token. Finish a reliable local integration and case study in approximately 3–6 days; keep the first milestone free and open source, with no paid setup/support experiment. Open PR #12 proposes Docker/secret-file support; coordinate rather than implement a competing path. [Source](https://github.com/feuerdev/keep-mcp/tree/main), [existing PR](https://github.com/feuerdev/keep-mcp/pull/12).

**feuer — strongest general engineering showcase.** Browser multiplayer RTS with hex terrain/pathfinding, building/resource systems and realtime sockets. `master` has sprite-based presentation and older Firebase integration; inspected `dev` at `562aa54e49092fc01f879f85d4aa1240c94999f6` has React/Vite/Pixi, Clerk, Zustand, PostgreSQL JSON world persistence, more mechanics and debug actions. This is substantive code, but not evidence of a balanced or reliable game. A large TODO list, untyped socket inputs, environment-dependent identity/debug behavior, reconnect/persistence and configuration concerns increase operational cost. First target a ten-minute seeded game, not an MMO launch; 8–15 days after build triage. Revenue is speculative and should wait for repeated playtests. [dev source](https://github.com/feuerdev/feuer/tree/dev), [master source](https://github.com/feuerdev/feuer/tree/master).

**PicChallenge — best compact consumer experiment.** The case-sensitive uppercase repository contains “Piccy”, a SwiftUI app importing images, presenting pairwise choices through `TournamentTree<UIImage>`, then showing a winner. A share extension uses an app-group handoff. It is more developed than `pic-challenge`, with a real local-only interaction rather than a backend/social-network requirement. No README, meaningful product validation or verified fresh native build. Its workspace uses sibling feuerlib; Podfile target names remain from the older app. The current `Set<UIImage>` and whole-image UserDefaults storage deserve replacement with stable IDs and bounded thumbnails/files. Validate choosing a keeper among similar shots; approximately 5–10 days after a Mac build and 6–10 user sessions. A one-time pro unlock is only a pricing hypothesis. [App state](https://github.com/feuerdev/PicChallenge/blob/main/Piccy/ViewModel/App.swift), [share extension](https://github.com/feuerdev/PicChallenge/blob/main/PiccyShare/ShareViewController.swift).

**yt-sponsor-detect — portfolio through measured ML.** MV3 extension captures caption requests, classifies sliding windows using local MobileBERT, caches estimated intervals and now offers reversible manual skip suggestions. Popup already supports categories/thresholds. Current README oversells offline operation: inference is local but captions originate from YouTube, and model setup downloads files. The original model script tuned thresholds on sample sentences. The draft adds reversible manual suggestions, explicit fail-open errors, pinned streaming setup and five passing real-source test files; the exploratory script remains `npm run evaluate`; those are not held-out model evaluation. The initial model-error fallback has now been replaced by explicit fail-open errors. Broad intervals, repeated captions, worker restart and settings/cache policy still need release evidence. Approximately 5–9 days for a credible annotated demo/evaluation. Paid differentiation is weak against SponsorBlock and existing ML alternatives; do not train on noncommercial data and assume commercial rights. [implementation](https://github.com/feuerdev/yt-sponsor-detect/tree/main/src), [experiment](https://github.com/feuerdev/yt-sponsor-detect/blob/main/test_classifier.js).

**Raytracer — focused fallback.** UIKit scene configurator with sphere/light/camera/quality controls; the renderer lives in feuerlib and supports intersections, shadows and recursive reflections. No current native build evidence. A reproducible release, architecture explanation and measured rendering tradeoffs would make a good 3–5 day case study after Mac setup. Do not turn it into a generic commercial renderer. [app](https://github.com/feuerdev/Raytracer), [rendering core](https://github.com/feuerdev/feuerlib/tree/main/feuerlib/Raytracer).

## External checks that affect the recommendations

- The official Google Keep API is aimed at enterprise administration, not a drop-in replacement for this personal-account integration. gkeepapi documents its unofficial status. This supports prioritizing local reliability and limiting hosted-account promises. [Google overview](https://developers.google.com/workspace/keep/api/guides), [gkeepapi](https://gkeepapi.readthedocs.io/en/latest/).
- SponsorBlock already provides crowd-sourced skipping, and sponsorblock-ml already explores automatic detection. Its README identifies noncommercial training-data licensing. The inference is that “local AI” alone is weak paid differentiation; the strongest portfolio contribution is a reproducible error/latency study. [SponsorBlock](https://github.com/ajayyy/SponsorBlock), [sponsorblock-ml](https://github.com/xenova/sponsorblock-ml).
- Piccy has competition in photo selection: WhichOne AI's store listing offers AI comparison and in-app purchases. This proves a category exists, not that a manual tournament will sell. Test a private, deterministic, local alternative with actual users. [listing](https://apps.apple.com/us/app/photo-comparison-whichone-ai/id6744938398).
- Chrome's MV2 deprecation blocks straightforward reuse of rerun-filter. [Chrome timeline](https://developer.chrome.com/docs/extensions/develop/migrate/mv2-deprecation-timeline).
- Commercial use of Reddit's Data API needs explicit approval; an old client library/credential flow is not proof of access. [Reddit access guidance](https://support.reddithelp.com/hc/en-us/articles/14945211791892-Developer-Platform-Accessing-Reddit-Data), [terms](https://redditinc.com/policies/data-api-terms).

## Recommended investment sequence

1. Spend the first 3–6 engineering days on keep-mcp's compatibility/onboarding/reliability evidence. In parallel only in the planning sense, schedule user interviews; no outreach was sent by this review.
2. Finish one feuer scenario and case study in the next 8–15 focused days. Freeze new mechanics; do not spend weeks on guilds, injury models or MMO operations.
3. Run Piccy discovery before a native rewrite. Continue if at least 6 of 10 target users complete the tournament unaided, 4 say they would reuse it weekly, and 3 explicitly accept the proposed one-time price. These are proposed decision thresholds, not observed results.
4. Bound sponsor detection to an evaluation milestone. Stop at a good technical write-up if reliability or differentiation is insufficient. No need to turn all four projects into businesses.

Raytracer is the best finite fallback if you prefer native/graphics work over operating a multiplayer demo. Portfolio and keyboard documentation amplify the selected projects but do not need new product scope. Revisit Big Pond only if the marine-life domain strongly motivates you and you can validate the data/content burden.
